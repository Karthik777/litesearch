tree

Document structure, so search can return whole sections with a breadcrumb

What a tree adds

A plain chunk store can tell you which 512-byte piece of text matches a query. It cannot tell you which chapter or section that piece belongs to, and a piece cut from the middle of a section often makes little sense on its own. This module records the structure of each document so search results can be placed and read in context.

At ingest, each document is split into a tree of sections. A node is one section: the document itself is the root node, and each heading (or chapter line, or citation, or group of pages) opens a child node below it. Every node has a node_id of the form <doc id>#<seq>, where seq is the node’s position in the document. Every chunk is stored with the node_id of the section it came from and its heading path, the chain of section titles from the document down to that section, such as Grahas › Saturn › Sade Sati. Results call this path the breadcrumb.

With the tree in place you get:

  • doc_search, hybrid search whose hits carry a breadcrumb and whose neighbouring hits in one section are joined;
  • sections, search that returns the best sections instead of chunks;
  • toc and read, which list a document’s sections and return one whole section, without computing any embeddings;
  • context, which gathers the best sections for a question, with their full text, for a language model to read.

Nothing here calls a language model. Node summaries are the first 300 characters of the section unless you pass your own function as summarize=.

Index (see the api page) calls all of these for you with its encoder already chosen. Call them directly when you build your own database().

Detecting structure

build_tree needs to know what marks a new section in a document. detect_mode looks for four kinds of signal and picks one mode per document:

mode sections start at typical source
markdown # headings markdown files, PDFs converted to markdown
verse verse citations such as || Mn_1.1 ||, and # headings Sanskrit texts from GRETIL or TEI
chapter lines like CHAPTER IV, Article 12 or ADHYAYA 3 scanned or plain-text books and legislation
window every 8 pages anything with none of the above

The window mode is the fallback, so every document gets a tree of some kind. A document counts as markdown with at least 2 headings if it has up to 3 pages, and otherwise at least 3 headings or one per 25 pages, whichever is more, so a one-page note with a single heading becomes one window. Some PDF converters mark every bold line as a top-level heading. When a document has more than 4 headings per page, all at the same depth, detect_mode does not trust them and uses chapter lines or windows instead.

In chapter mode, struct_levels decides how the structural words nest. Known words have a fixed order: BOOK, TITLE, PART and similar come first, then CHAPTER, then SECTION, then ARTICLE, RULE and CLAUSE. Levels are then renumbered from 1 with no gaps, so a document that only uses “Article” gets its articles at level 1. At most 4 levels are kept.

detect_mode checks for verse mode first. It chooses verse when at least 3 pages carry a citation, citations appear on more than a fifth of the pages, they name at least two levels (such as chapter and verse), and they outnumber markdown headings.

TreeNode

def TreeNode(
    seq:int, title:str, level:int, parent:int | None=None, page_start:int=0, page_end:int=0, segments:list=<factory>,
    children:list=<factory>, summary:str=''
)->None:

One section of a document, where seq is its position in the node list and parent is the seq of the section above it.

build_tree takes a list of (page number, text) pairs and returns the nodes as a flat list, where nodes[seq] is the node with that seq and each node’s parent is its parent’s seq. The same list is written to the nodes table, and toc() rebuilds the nesting when you ask for it. A heading is placed under the nearest earlier heading of a shallower level, so a document that starts at ## or jumps from # to ### still nests correctly.

In verse mode, a citation like Mn_1.1 gives the verse’s address: every part except the last names the division it belongs to, so Mn_1.1 opens a node Mn 1 for chapter 1. Verse mode also reads # headings, because some texts name their sections (## dhyanam) and carry no citations. Citation levels are counted from the heading above them.

heading_path builds the breadcrumb for a node. If a segment repeats the one before it, it is dropped, so a PDF whose first heading is the same as the document title reads Field Manual › Chapter 1 and not Field Manual › Field Manual › Chapter 1.

The breadcrumb is stored with every chunk in the heading column, and by default it is also prepended to the chunk’s text before embedding, so the vector reflects where the text sits. It is not added to the full-text index: a keyword search for a section title finds only chunks whose own text contains it.

assert detect_mode([(i, 'prose') for i in range(20)]) == 'window'
assert len(_plain) == 4, [n.title for n in _plain]   # root + ceil(20/8) windows

The tables

get_tree adds three tables beside a chunk store and four columns to the store. The chunk store is still an ordinary store, so full-text search, the ANN index and db.search work on it unchanged.

docs    id · title · source · kind · pages · meta · hash · added_at
sources source · doc_id · added_at
nodes   id ('doc#seq') · doc_id · parent_id · level · seq · title ·
        page_start · page_end · summary · nchunks
store   content · embedding · metadata · doc_id · node_id · page · heading   [+ FTS5, +ANN]

For the default store the tables are called docs and nodes; for a store called papers they are papers_docs, papers_sources and papers_nodes.

A document’s id is a hash of its source and its title. A file’s source is its resolved path, so a relative path, an absolute path and a symlink to one file are one source. hash is a hash of the document’s (page, text) pairs, and sources maps every source to the document holding its text:

  • The same source with the same text again is skipped as unchanged.
  • The same source with changed text replaces the old chunks and nodes, and keeps the id.
  • A different source with text already stored is skipped as same text as <source>, and gains a row in sources pointing at the stored document. A copy, or a string with the same text, adds no chunks.
  • A document goes when the last source pointing at it does. delete_source forgets one source. delete_doc forgets the document’s own source; text another source shares stays, under that source. Editing a file whose text another source shares moves the old text to an id of its own for that source first.
  • A text added with no source is keyed by its title. A second, different text under the same title is skipped, as before 0.1.50, because a title names nothing on disk.

force=True rebuilds a document even when its text is stored, which is how a new chunker, mode or meta_fn reaches text already ingested. A title or kind change on one source builds a new document under the new id and drops the old one.

A store written before 0.1.50 has no sources table and no hashes. get_tree creates the table and fills it from docs.source. Re-adding a file by the path it was first added under moves its document to the resolved-path id, keeping its vectors, and re-embeds it once to record its hash. Duplicates an old store already holds go as their sources are re-added.

Ingestion

There are three ways in, from the most control to the least:

  • add_doc takes text you have already extracted, as a string or a list of (page number, text) pairs. It builds the tree, chunks each section, embeds the chunks with emb_fn and stores them. Use it when your app fetches or converts documents itself.
  • add_file reads one file and passes its pages to add_doc.
  • add_dir does the same for every document file under a folder, or for a list of files.

Each returns a dict per document with its doc_id, title, kind, number of nodes and number of chunks, or a skipped reason when its text is already stored: unchanged, or same text as <source>.

emb_fn takes a list of strings and returns one vector per string. Without it, chunks are stored with no embedding, which is enough for keyword search, toc and read.

Chunks are cut within each section, never across a section boundary, using chunk_markdown’s default chunker unless you pass chunker=, any chonkie chunker. A chunk shorter than 40 characters is joined to the chunk before it instead of being stored alone. Two chunks with the same text in different sections are both kept, because the row id is a hash of the node id and the text.

A chunker sees one segment of a section at a time. Some readers produce very small segments, such as one verse per page, and a chunker aiming at 700 characters never reaches that size on a 60-character verse. A chunker can ask for its small chunks to be joined across segments by having pack_cited=True and a target size; pack_target reads the size a chunker asks for, and _pack_segments then joins consecutive chunks of one node up to target characters. Ordinary chunkers have neither attribute and are unaffected.

add_doc(defer=...) collects the chunks in a list instead of embedding and storing them, and store_chunks embeds and stores such a list later. add_doc(jobs=...) collects the whole write, and _commit stores a batch of them: chunks first, then nodes, doc rows and sources. add_dir uses this to embed chunks from many documents in batches of 2,000 (embed_batch), which is faster than one call per document, and a run that fails before a batch is stored leaves the documents it would have replaced whole.

add_file handles document files: PDF, markdown, plain text, reStructuredText, notebooks, XML, HTML and CoNLL-U. XML, HTML and CoNLL-U are read as plain text unless a registered profile claims them. A PDF is converted to one markdown page per PDF page by pdf_parse, and its images are saved under db.assets(), a folder beside the database file. A notebook becomes one page with its cells joined. Any other file is read as one page of text. The title defaults to the file name with underscores and hyphens turned into spaces, and kind defaults to the extension (notebook for .ipynb).

Source code does not fit a heading-based tree. To index code, use Index.add_code (see the api page), which cuts it into top-level functions and classes using Python’s syntax tree.

A Profile (see the data page) describes how to read one kind of document: its parser, chunker, tree mode and per-chunk metadata. When a registered profile claims a file, add_file uses it instead of the steps above. This is how a TEI edition of a Sanskrit text is told apart from any other .xml file. Pass profile= with a name to choose a profile directly, which is the only way to reach one that cannot be detected from the file.

add_dir ingests every file under dir whose extension is in types, or exactly the paths in files=. Files whose text is already stored are skipped, and a file edited since it was added is replaced. Each call writes to one store, because the embedder and the ANN index belong to that store; to send files from one folder to different stores, call it once per store with files=.

Parsing PDFs, notebooks and XML is slow, so when 4 or more such files are in the batch, add_dir parses them in a pool of worker processes (n_workers overrides this; 0 means no pool). In one measurement, parsing took 3.55 of the 5.31 seconds needed to ingest 8 PDFs, while 150 markdown files took 2.7 milliseconds to read in total, too little for a pool to help, and HTML is read the same way. All writes stay in the main process.

By default the full-text index is updated as each chunk is written. With bulk=True, add_dir turns that off during the load and rebuilds the full-text index once at the end. This is faster for a large first load, but keyword search misses the new documents until the load finishes, so use it only when nothing searches the store meanwhile. The ANN index is rebuilt once at the end either way.

stop is a callable add_dir asks before each file, for a caller that may need to cancel a long load. When it returns True, add_dir stops: the files already stored stay stored and indexed, a parse in flight finishes, and no further parse starts. Given stop, the result is an L whose cancelled says whether files went unread and whose unread lists them. Without stop, the result is the plain list it always was.

Reading the structure

These functions read the tree and compute no embeddings, so they are fast and need no encoder. They suit an agent or a reader that browses: look at the table of contents, pick “the chapter on remedies”, and open it.

  • toc(doc) returns each document’s tree as nested dicts with node ids, titles, levels, page ranges, chunk counts and summaries. doc may be a doc id or part of a title; leave it out for every document. max_depth (3) limits how deep it goes.
  • read(node_id) returns one whole section: its chunks joined in order, with the text of all its subsections by default (children=False for just the section), up to max_chars (20,000). It also returns the breadcrumb, page range, summary and the ids of its direct children.
  • breadcrumb(node_id) returns just the title path.

Retrieval that knows about structure

Hybrid search runs two searches and combines them. The keyword search uses SQLite FTS5, a full-text index ranked by bm25, which favours chunks that contain the query’s rarer words. The vector search compares the query’s embedding with each chunk’s embedding. Reciprocal Rank Fusion (RRF) merges the two ranked lists: each chunk scores 1/(rrf_k + rank) in each list it appears in, so a chunk ranked well by both searches beats one ranked well by only one. rrf_k defaults to 60.

doc_search is db.search for a tree store, with two additions. Every hit gets a breadcrumb. And hits from the same section at most gap pages apart (1 by default) are joined into one hit, so a reader gets one passage instead of two halves; the joined hit keeps the best rank and score of its parts and counts them in _nspan. rerank=True reorders the top 30 candidates with a flashrank cross-encoder, a small model that reads the query and each chunk together; it is slower and downloads a 3 MB model on first use.

sections answers “which sections match”, returning sections instead of chunks. It gathers chunk hits (limit × fanout, at least 20), groups them by node, and scores each section by its best hit (score='max'). Each section comes with its breadcrumb, summary, page range, up to per snippets and a read string naming the call that opens it. score='mean' averages the hits and score='sum' adds them. Summing favours long sections that collect many weak hits: on 150 known-item queries over 486 pages of EU legislation (07_doc_eval), sections scored 0.852 MRR with sum against 0.957 with max on verbatim queries, and 0.304 against 0.505 on reworded ones.

Use doc_search when you want passages to show or quote. Use sections when the answer is a place in a document, such as which article or chapter, and you will read it next.

doc_search(adaptive=True) changes the weight of each list before fusion using adaptive_weights, three fixed rules: when one search returns nothing, the other gets all the weight; a quoted phrase adds 0.6 to the keyword weight; and a query where at least half the words look like names or identifiers (capitalised, containing digits or underscores) adds 0.4. It is off by default because on the natural-language queries in 07_doc_eval the rules never fired.

context gathers what a language model needs to answer a question from a document collection, in one call. It returns AttrDict(query, results, related):

  • results holds up to sections (6) of the best sections. Each has its full text from read (up to max_read, 6,000 characters), breadcrumb, pages, summary, score, snippets, source file name, and with tree_ctx=True its place in the tree from node_context: its parent, up to 8 sibling sections and up to 12 child sections. A document’s root node is never returned as a result, and two sections with the same breadcrumb are returned once.
  • related holds up to related (8) other sections that came up in a second hybrid search, with their title and breadcrumb but no text. Set vector=False to skip it.

Extra keyword arguments such as ann, rerank, fts_pre and rrf_k are passed to every search it runs.

Limits

  • No language model is used. A summary per node is what toc() shows a reader deciding where to look, and the default is only the first 300 characters. Pass summarize= to write better ones.
  • Chunk size matters more than anything else in this module. In 07_doc_eval, cutting smaller chunks instead of page-sized ones raised MRR on reworded queries from 0.354 to 0.532, while breadcrumbs in the embedding and span joining changed it by less than 0.01. The default chunker is chunk_markdown; pass a better splitter as chunker=.
