Turn PDFs, text and code into chunks ready to index, and turn a user’s question into an FTS5 query

Before a document can be searched it has to be cut into pieces. A search returns pieces, not whole files: a 15-page paper should come back as the paragraph that answers the question, not as page 1. Each piece is called a chunk, and the object that decides where to cut is a chunker.

This page holds the tools that read files and produce chunks, plus the functions that clean up a query before it reaches SQLite’s full-text search. Most applications never call them directly, because Index.add and add_dir in litesearch.tree call them for you. Reach for them when you build your own pipeline on database(), or when you want to see what a file turns into before you index it.

The sections, in order: reading PDFs, chunking text, reading code and other files, profiles for special document kinds, listing installed packages, preparing queries, and building a PDF from images.

Reading PDFs

pdf_oxide opens and reads PDFs. litesearch adds a few methods to its PdfDocument class, each taking an optional page range st to end (0-based, end excluded, all pages by default):

method returns
pdf_texts the plain text of each page
pdf_markdown each page as markdown, with headings and tables marked up
pdf_links every hyperlink in the document, as a list of URLs
pdf_images metadata for every image, or with output_dir, saves the images and returns each page’s text with links to them
pdf_tables every table found, with its rows, cells and position
pdf_spans runs of text with their font size, weight and position on the page

These are thin wrappers over pdf_oxide and do no cleaning. For indexing, use pdf_parse below instead.

pdf_parse is the function to use when you index a PDF. It returns a list with one markdown string per page. The work is done by pdflite, a separate package whose helpers are re-exported here. pdflite converts each page with pdf_oxide, joins words hyphenated across a line break, and collapses the extra spaces and blank lines the conversion leaves. Some pages come out with their columns scrambled, so that a figure such as a price ends up on a line of its own, away from its label. For those pages pdflite tries the plain-text layer instead and keeps whichever version strands fewer values.

A scanned book has no text layer at all, only page images, and needs OCR (optical character recognition, reading the text from the images). ocr_selection controls it. With 'auto', the default, OCR runs over the whole document when pdf_oxide reports any page as scanned. 'on' always runs it and 'off' never does. OCR needs the liteparse package, which is not installed with litesearch.

Images on the pages are saved to out_path/image_dir, and the markdown links to them by that relative path. With no out_path, they go to pdfs/images under the current folder. preserve_layout=True keeps indentation and runs of spaces, which tables laid out with spaces need.

Index and add_dir call pdf_parse and keep its page boundaries. The document tree and the default chunk size were both measured on this one-string-per-page split.

Chunking text

The default chunker is chonkie’s FastChunker, set to 512 bytes. It walks through the text and cuts each piece at the last newline, full stop or question mark before the 512-byte limit, so a chunk usually ends at the end of a line or sentence. Where there is none, it cuts at the limit. 512 bytes is about 500 characters of English, or about 170 characters of Devanagari, which takes three bytes per letter. evals/ measured 512-byte chunks against page-sized ones, and the smaller chunks found the right section more often.

SafeFastChunker

FastChunker cuts by byte position, so a cut can land in the middle of a character that takes more than one byte, such as an em dash, a curly quote or any Devanagari letter. It then raises UnicodeDecodeError, and a long unbroken paragraph with one such character, which most scraped web pages contain, is enough to trigger it. SafeFastChunker moves each cut back to the start of the character it split. No text is lost; a cut moves by at most three bytes. litesearch uses it everywhere in place of FastChunker.

There are three ways to chunk text:

  • chunk_markdown(text) returns the chunks as a list of strings. Use it when you only need the text.
  • chunk_spans(text) returns (start, end, text) for each chunk, as character positions in the string you passed in. Use it when you need to map a chunk back to its place in the source, for example to highlight a hit inside the full document.
  • PdfDocument.pdf_chunks() runs pdf_parse and then chunk_markdown on each page, and returns (page, chunk_idx, text). Pages are counted from 1 and chunk_idx restarts at 0 on each page. Use it to index a PDF page by page without building a document tree.

All three take an optional chunker, any chonkie chunker, if 512 bytes does not suit your text.

Reading code and other files

Code needs different chunks from prose. A 512-byte cut through the middle of a function is useless as a search result, so code is cut at definitions instead: each top-level function or class becomes one chunk. Every chunk is a dict with the text under content and facts about where it came from under metadata, which is the shape get_store and sync in litesearch.core take.

file_parse(path) picks a reader by the file’s extension:

extension reader one chunk per
.py pyparse top-level function or class, plus imports or assignments if asked
.ipynb ipynb_parse notebook cell, of any type
.js, .ts, .go, .rs and the rest of code_exts non_py_sigs signature, with the body replaced by {...}
.pdf PdfDocument.pdf_chunks 512-byte chunk
.md chunk_markdown 512-byte chunk
.txt chunk_texts 512-byte chunk, cut at blank lines where possible

Any other extension gives an empty list. For languages other than Python only the signatures are indexed, through the codesigs package, so a search finds the function by its name and parameters but not by what its body does.

To read many files at once, pkg2chunks reads every file of an installed package and dir2chunks every file under a folder. Both are further down.

Profiles: how to read one kind of document

Some documents need more than a different chunker. A Sanskrit text in TEI XML, for example, needs a reader that knows an <lg xml:id=...> element is a verse, a tree that treats a citation as the start of a chapter, and a chunker that cuts at the daṇḍa (।), the mark that ends a half-verse. A Profile bundles all of these for one kind of document and gives them a name. When add_file or add_dir in litesearch.tree reads a file, it asks profile_for whether a registered profile claims it. If one does, the profile’s parts are used; if none does, the file goes through the default pipeline above.

Profile

The fields, all optional except name:

field what it is
exts the extensions the profile claims, comma-separated, such as '.xml,.txt'; empty claims every extension
detect a function from the file’s text to True or False, used when an extension is shared
parse a function from a path to (pages, meta), used instead of the default reader
chunker a function returning a chonkie chunker, used instead of the 512-byte default
mode the structure mode for build_tree, used instead of detecting one
kind the document kind recorded on the document’s row, so searches can filter on it
meta a function from a chunk’s text to a dict, stored in the chunk’s metadata column

meta lets a profile attach facts that only it can work out. ganapati’s Sanskrit profile stores each verse’s metre there. The metadata column is part of the full-text index that get_store builds, so those facts become searchable and filterable with no change to the table.

profile_for

profile_for returns the first registered profile that claims a file, or None. It checks the extension first and then calls detect on up to the first 60,000 characters of the file. An extension alone is never enough to decide: .xml may be TEI, a vedicreader export or something unrelated, and .txt may be anything. A profile that has no detect and shares its extension with another can still be chosen by passing name=. register_profile adds a profile, replacing any with the same name.

Another package can add profiles without litesearch importing it, and without importing litesearch itself. It declares an entry point in the litesearch.profiles group that names a function, and that function calls register_profile. The first call to profile_for runs load_plugins, which calls each such function once. A plugin that raises is skipped with a warning, and the others still load. ganapati registers its Sanskrit profiles this way:

[project.entry-points."litesearch.profiles"]
ganapati = "ganapati.lemma:register_profiles"

from fastcore.test import test_eq

bad = SimpleNamespace(name='bad', load=lambda: 1/0)
import warnings
with warnings.catch_warnings(record=True) as ws:
    warnings.simplefilter('always')
    test_eq(load_plugins([ep, bad]), ['zz'])             # a broken plugin warns, the rest still load

pyparse reads a Python file, or a string of code passed as code=, and returns one chunk per top-level function and class. Methods stay inside their class’s chunk, and a function defined inside another function stays inside it. The metadata gives the name, the node type (FunctionDef, ClassDef and so on), the first and last line, the file’s path and its modification time. With code= there is no file, so path is the string 'None' and uploaded_at is None.

It reads only the top level of the module and splits the source into lines once per file. On 400 files of the transformers package that took parsing from 23.4 s to 3.3 s with the same chunks.

For a JavaScript file file_parse hands over to codesigs, which returns each function’s signature with its body replaced by {...}. The top-level const and let lines are not chunks.

def parse_js():
    from textwrap import dedent
    from tempfile import NamedTemporaryFile as ntf

    js_code = dedent("""
        const htmlElement = document.documentElement;
        const mediaQuery = window.matchMedia('(prefers-color-scheme: dark)');
        const vr = '__VR__';
        let __VR__ = JSON.parse(localStorage.getItem(vr) || '{{__state__}}');
        function storeState(key, value) {__VR__[key] = value; localStorage.setItem(vr, JSON.stringify(__VR__));}
        function getState(key){return __VR__[key];}
        function removeState(key) {delete  __VR__[key]; localStorage.setItem(key, JSON.stringify(__VR__)); }
        function setTheme(color,fn=null, ...args) {
            if (color === null || color === undefined) {return;}
            htmlElement.classList.remove(__VR__.theme);
            htmlElement.classList.add(color);
            storeState('theme', color);
            if (typeof fn === 'function') {fn(...args);}
        }
    """)

    with ntf('w+', suffix='.js', encoding='utf-8') as f:
        f.write(js_code)
        f.flush()  # Ensure content is readable by file_parse from disk
        print(file_parse(Path(f.name)))

globsafe takes the parameters of fastcore’s globtastic and returns the same files, but skips an entry it cannot read. globtastic raises OSError at a symlink that points at itself, and returns a dangling link as if it were a file. globsafe leaves out both, and an unreadable folder, and does not enter a symlinked folder that leads back into one of its own ancestors. pkg2files and dir2files use it.

Preparing a query for full-text search

SQLite’s full-text search engine, FTS5, finds rows that contain the words of a query and ranks them with bm25, a score that rewards rare words and words that appear often in a short row. Its query language gives several characters a special meaning: * marks a prefix, " quotes a phrase, parentheses group terms, ^ anchors a term to the start of a column, - belongs to the syntax for choosing columns, and OR, AND and NOT combine terms. A word may contain only letters, digits and _ unless it is quoted. A question typed by a user can therefore fail with a syntax error, and even a valid one asks for too much: by default FTS5 returns only rows that contain every word, including words such as “how” and “does”.

These functions turn a user’s text into a query FTS5 accepts and that finds more:

  • clean replaces the operator characters * , " ( ) ^, and a - directly before a word, with spaces. It returns None for an empty query. Underscores are kept, so fts_search stays one word.
  • kw splits the text into words with the Unicode word-boundary rules (UAX #29, through apsw), lowercases them, and drops one-letter words and the stopwords in QSTOP, a list of common English words such as “the”, “how” and “does”. If every word is a stopword, it keeps them all.
  • add_wc adds * to each word so it also matches longer words that start with it: sample* matches “samples”. A word with characters other than ASCII letters, digits and _, such as pathfinder's or any Devanagari word, is quoted first, because FTS5 accepts it only as a quoted string.
  • mk_wider joins the words with OR, so a row needs only one of them to match. bm25 still ranks rows that match more of the words higher.
  • pre runs all four in that order: clean, kw, add_wc, mk_wider. Each step after clean can be turned off.

Database.search passes the keyword half of every search through pre unless you set fts_pre=False. evals/ measured it at +0.016 to +0.093 weighted MRR. To build a query from a list of terms you already have, rather than from a user’s sentence, use fts_or, fts_and or fts_phrases in litesearch.core, which quote each term.

Building a PDF from images

Photos or scans of pages often arrive as image files. images_to_pdf puts a list of images into one PDF, one image per page, so they can go through the same PDF pipeline as any other document, OCR included. It accepts Pillow images, image bytes or file paths, and writes the PDF itself from the PNG data, needing only Pillow and the standard library. img2png converts one image to RGB PNG bytes, and png_det reads a PNG’s width, height and compressed pixel data, which a PDF can embed unchanged.

The functions were written when pdf_oxide’s Pdf.from_image methods produced an empty 1.3 KB file. With pdf_oxide 0.3.77, Pdf.from_image_bytes returns a full-size file, so either route now works.

Copy the bundled SKILL.md into the .agents, .claude and .Codex skill folders, or with dry_run only print where.

import io, tempfile, contextlib
from litesearch import data as _data
# dry_run used to print "Installed" too; the module's copy is used because it finds SKILL.md beside its own file
with tempfile.TemporaryDirectory() as tmp:
    with contextlib.redirect_stdout(io.StringIO()) as o: _data.mv_skill_md(dry_run=True, dir=tmp)
    assert o.getvalue().startswith('Would copy') and 'Installed' not in o.getvalue(), o.getvalue()
    assert not list(Path(tmp).rglob('SKILL.md'))
    _data.mv_skill_md(dry_run=False, dir=tmp)
    for d in ['.agents', '.claude', '.Codex']: assert 'litesearch' in (Path(tmp)/d/'skills/litesearch/SKILL.md').read_text()
