Building blocks for litesearch

This page covers the lower of litesearch’s two routes. database() opens a SQLite database ready for search, get_store creates a store in it, and Database.search runs a hybrid query against that store. The rest are the parts those three are made of, which you can also call on their own: keyword search, exact and approximate vector search, rank fusion, spelling correction and a few tools for writing from several threads.

A store is a table with one row per chunk of text. It has a content column for the text, an embedding column for the text’s vector, a metadata column for JSON, and an FTS5 full-text index over content and metadata that SQLite keeps up to date as rows change. If you do not need your own schema or SQL, [Index](https://Karthik777.github.io/litesearch/api.html#index) sets all of this up for you.

Tokenizers

FTS5 does not index text as written. A tokenizer splits it into tokens, the words FTS5 looks up, and can change them on the way in, for example by lowercasing or stemming (reducing running to run). The query goes through the same tokenizer, so a query matches a row when they share tokens. A store’s tokenizer is fixed when its table is created.

The common FTS5 setting, porter, stems the output of FTS5’s default tokenizer unicode61, which splits on anything that is not a letter or a digit. That breaks identifiers apart: fts_search is indexed as ft and search. It also breaks Devanagari words into pieces, because it treats the vowel signs as separators.

litesearch’s default chain is porter simplify casefold 1 sanskrit unicodewords. Each tokenizer passes its output to the one on its left. unicodewords splits text into words by the Unicode word-boundary rules (UAX #29), which keep fts_search whole. sanskrit adds, beside each word, copies reduced to plain ASCII, so a Devanagari or romanised word can be found by its ASCII spelling. simplify casefold 1 lowercases, and porter stems English. On this chain fts_search stays one token, and Krishna duties gives the tokens krishna, with the ASCII copy krsna beside it, and duti.

The order matters. sanskrit sits inside porter, so the ASCII copy is made from the original word and then stemmed the same way an ASCII query is. With sanskrit outside porter, धर्मक्षेत्रे would be indexed as dharmaksetre while the query dharmaksetre stems to dharmaksetr, and the word could not be found by its own spelling. That happened to 3 of 14 ordinary Devanagari words tested.

_tokenizers_ok checks that the whole chain can be built on a connection, which is the only reliable test: simplify refuses to be built on its own, so checking each name separately would report a working chain as broken.

Writing rows

process_content is the general way to add chunks to a store. It embeds them with your encoder function if asked, gives each row an id (a hash of its content, so the same text gets the same id), and upserts them, which inserts new rows and updates rows whose id already exists. It writes chunk rows per transaction. embed_chunk is the embedding step on its own.

write_txn opens a write transaction with BEGIN IMMEDIATE, which takes SQLite’s write lock at the start instead of at the first write, so two writers cannot both start and then deadlock. A write_txn inside another one joins the outer transaction. db_lock is the lock litesearch holds while it reads and writes on one connection, so threads that share a connection do not interleave. A thread may hold db_lock while it waits on workers that read the same connection, as Kosha.context does, so the read paths never take it: on an ordinary connection get_index and usearch_sql load under a lock of their own.

busy_window is for opening connections while another process holds the write lock. SQLite waits up to the busy timeout for a lock before raising BusyError. apsw’s recommended settings, which apswutils turns on, set a 100 ms timeout and run PRAGMA optimize while a connection is being opened, before your code can change the timeout. busy_window raises that default for every connection opened inside the block and restores it afterwards. It counts nested windows, so the outermost one restores the original value. database(busy_timeout=) uses it for you.

Stores

get_store creates a store, or opens it if it exists. By default the id column is an integer that SQLite assigns. With hash=True, id is a SHA-1 hash of the content instead, so inserting the same text twice leaves one row. That suits code and other text you re-ingest often. With ann=True, the store also gets an HNSW index for fast vector search, described below.

upsert_all writes rows with a single prepared statement per batch: rows whose primary key is new are inserted, and rows whose key already exists are updated.

A store records which encoder and which tokenizer created it, in a table called store_meta. Reopening it with a different one raises StoreMismatch.

The vectors from two encoders cannot be compared, even when they have the same length. potion-base-8M and potion-multilingual-128M both produce 256 numbers per text, so nothing about the vectors shows that they came from different models. Before this check, opening a store with the wrong encoder added vectors from another model to the same index, and searches returned wrong neighbours without any error. The tokenizer is recorded for the same reason: a query tokenized differently from the index looks for tokens the index does not contain. An encoder with no name records '', and an empty value never conflicts, because litesearch cannot tell what a custom encoder is.

When usearch’s HNSW index fails its probe (see postfix), get_index returns an ExactIndex instead. It has the methods of usearch’s Index that litesearch calls, holds the vectors as one float32 matrix, and searches all of them with numpy, so results are exact. _np_dist computes the four metrics as usearch does, and the numpy path of vec_search uses it too. ExactIndex.save writes no index. It leaves a .stale file beside the sidecar, so the next process with usearch on rebuilds the index from the table instead of loading one that misses the rows written meanwhile.

Searching one leg at a time

A hybrid search has two legs, a keyword search and a vector search. Each is available on its own, on any table, not only on stores.

fts_search runs an FTS5 query and returns rows ordered by bm25 rank. FTS5 reports bm25 as a negative number in the rank column, so lower is better.

vec_search is exact vector search. It computes the distance from the query vector to every row’s embedding in SQL and returns the nearest rows, with the distance in _dist. When usearch’s SQLite extension is off, it computes the same distances with numpy and returns the same rows; a where that names _dist works only in SQL. It reads every row, so it is always correct and gets slower as the table grows; up to a few thousand rows it is fast. ann_search, further down, is the approximate alternative for large stores.

Both legs take the vector’s number type as dtype, and getting it wrong is silent in SQL. model2vec encoders return float32 and FastEncode returns float16. If float32 bytes are searched as float16, the distance function reads them as twice as many float16 numbers, many of them invalid, and returns NULL for every row. The vector leg then comes back in table order, and a hybrid search quietly becomes a keyword search. _dtype_check warns when the dtype differs from the one the store’s HNSW index recorded, or when every distance comes back NULL or 0.

Loading in bulk

FTS5 keeps its index current through triggers that run on every insert, update and delete. bulk_load removes those triggers for the duration of a with block and rebuilds the full-text index once at the end. Use it for large offline loads. During the block the full-text index does not see the new rows, and for a small update a full rebuild costs more than the triggers would have.

Rows similar to a row

ann_neighbors finds the rows nearest an existing row, such as “more like this” for a search result. It uses the vector the HNSW index already holds for that row, so it loads no model and embeds no text: the call is one index lookup and one query for the matching rows. That makes it cheap enough to run every time a user moves to a new result.

ann_vec returns the stored vector for a row’s key (its rowid), or None when the index does not hold it. ann_neighbors leaves the starting row out of its results unless you pass include_self=True.

Reciprocal Rank Fusion

rrf_all merges ranked lists into one. Each row earns weight / (k + position) from every list it appears in, counting positions from 0, and the amounts add up. With the default k=60, the top row of a list earns 1/60 and the row at position 60 earns half that. A row that appears in two lists collects two amounts, so it usually beats a row that tops only one. Because RRF uses positions only, it can merge lists whose scores are not comparable, such as bm25 ranks and vector distances. Rows are matched across lists by id_key, rowid by default. weights gives each list more or less influence.

Sharing one connection between threads

apsw, the SQLite driver underneath fastlite, raises ThreadingViolationError when one thread calls into a connection while another thread is using it. apsw cursors are lazy: a thread reading rows keeps the connection busy between rows, so even two readers collide.

Conn wraps a connection so threads can share it. Each statement runs and is read to the end under one lock, and a thread that opens a transaction keeps the lock until the transaction ends. Rows holds the rows a statement returned, with the parts of the apsw cursor interface that apswutils uses: iteration, fetchone, fetchall, row_trace and the column description. Cur is the cursor Conn.cursor() returns.

Reading every row at once costs memory on a large SELECT, which is why sharing is off by default and database(shared=True) turns it on. One caveat: apswutils’ Table.insert reads last_insert_rowid() in a second statement, and another thread’s insert can run between the two. If you read last_pk after an insert on a shared connection, hold db_lock(db) around both.

Opening a database

database() opens a connection and prepares it for search. It registers apsw’s FTS5 tokenizers and litesearch’s sanskrit tokenizer, and checks that the default chain works. It does not load usearch’s SQLite extension, which provides the vector distance functions: vec_search loads it into the connection on first use, through Database.usearch_sql(), after the probe in postfix has passed. Keyword search never loads it. Call db.usearch_sql() yourself before calling distance_* functions in your own SQL; it returns False when sem_search=False or the probe failed.

database() turns on WAL mode by default, which lets readers continue while a writer writes.

Tokenizers are registered on the connection, not stored in the file, because FTS5 looks a tokenizer up by name every time it reads or writes the index. Any connection that opens a litesearch store must register them first, and database() does.

The next tests cover writing from several threads, each with its own connection. apswutils turns on apsw’s recommended settings, which give a new connection a 100 ms busy timeout and run PRAGMA optimize while it opens. When several threads opened connections and wrote at once, that 100 ms ran out, BusyError was raised, and whole batches were lost without notice.

_wdb = database(sem_search=False); _wt = _wdb.get_store(name='w', hash=True)
with write_txn(_wdb): _wt.insert({'content':'a'})
try:

with write_txn(_wdb):

Nested busy_window blocks keep the raised timeout until the outermost one exits, and only that exit restores the original value.

Building and ranking keyword queries

Query strings

An FTS5 query is a small language of its own. Words are combined with AND, OR and NOT, text in double quotes is a phrase, * after a word matches any word starting with it, and column : (...) restricts a match to one column. Text typed by a user can contain a quote, a hyphen or the word OR, which FTS5 then reads as syntax, and the query fails or means something else.

fts_or, fts_and and fts_phrases build FTS5 queries from a list of terms. Each term is put in double quotes, so whatever it contains is matched as text, and repeated or empty terms are dropped.

  • fts_or matches rows containing any of the terms. Use it for recall: a word together with its spelling variants or synonyms, such as ["bhisma", "bhishma"]. column= limits the match to one column or a list of columns.
  • fts_and matches rows containing all of the terms. With prefix_last=True the last term also matches as a prefix, for search-as-you-type, where the last word is usually unfinished.
  • fts_phrases matches rows containing any of the phrases “term suffix”. Passing ("is", "means") as suffixes finds sentences that define a term, such as “comparison is knowing by likeness”.

These differ from pre() in litesearch.data, which Database.search applies to a raw query: pre() drops stopwords, adds a prefix wildcard to every word and joins them with OR.

Ranking by query terms

bm25 has two weaknesses for this kind of search. A short row that repeats a common query word can outrank a long row that contains a rare one, and bm25 scores from two different FTS tables are on different scales and cannot be compared. rank_fts re-orders hits by three keys in turn: how many of the query’s terms a hit contains, then the summed IDF of those terms (IDF, inverse document frequency, is higher for terms that appear in fewer rows), and then bm25 relative to the best hit in its own list. VedicReader’s Ask feature fetches 200 candidates per table (fts_depth) before this re-ranking. Together with correct, it raised the number of questions with a hit from its library from 69 to 84 out of 100.

rank_fts takes the hits of one FTS query, or a list of hit lists from several tables. Each entry in terms is either one key or a set of keys that count as one term, such as a word together with its corrections or synonyms. keys turns a hit’s text into keys of the same kind; by default it folds each word with fold_token, so Bhīṣma becomes bhisma. df gives each key’s frequency: a row count, an occurrence count, or the (rows, occurrences) pair that fts_vocab returns. n is the number of rows in the corpus and defaults to the sum of the counts in df; when two hits contain the same number of terms, its value does not change their order. correct suggests what a query word was meant to be when it is not in the index. Pass it the vocabulary from fts_vocab. It returns [word] when the word is indexed, and otherwise up to top index terms, most frequent first, that start with the same letter and are close to it:

  1. terms that are the word with two neighbouring letters swapped (comparsion to comparison), at any length;
  2. if there are none and the word has at least min_len letters (7 by default), terms within edits insertions, deletions, substitutions or swaps;
  3. if there are still none, skeleton=True and the word has at least five letters, terms with the same first letter and the same consonants in the same order (bhishma and bheeshma both reduce to bhshm).

Edits wait for seven letters because a short word one edit away from an indexed word is usually a different word, such as router and route.

Reranking

A cross-encoder is a small model that reads the query and one candidate passage together and scores how well they match. It is more accurate than comparing embeddings, which are computed for the query and the passage separately, and much slower, so it is used only on the top few dozen candidates of a fast search. rerank_hits reorders hits this way with flashrank, which must be installed separately. RERANK_FANOUT (30) is the number of candidates doc_search and Index.search give it.

Database.search: the hybrid query

Database.search is the hybrid search on one store. It runs the keyword leg (FTS5, by default with the query passed through pre()) and the vector leg (exact vec_search, or ann_search with ann=True), then merges them with RRF. You supply the query text and the query’s embedding, as bytes in the store’s dtype. With rrf=False it returns both lists unmerged, which is useful for debugging a ranking. It returns None for an empty query.

There are three search methods at different levels, and they differ in what they know about your documents:

  • Database.search, here, knows only the store. Hits are rows.
  • Database.doc_search, in litesearch.tree, runs this search on a store with a document tree, merges neighbouring hits from the same section into one, and adds each hit’s heading path.
  • Index.search, in litesearch.api, calls doc_search with its own encoder, so you pass only the query text.

Approximate vector search with HNSW

Exact vector search reads every row, so its time grows with the store. An approximate nearest-neighbour (ANN) index answers the same question much faster on large stores by giving up a little accuracy: it may occasionally miss one of the true nearest rows. litesearch uses usearch’s HNSW index. HNSW (hierarchical navigable small world) is a graph in which each vector is linked to vectors near it, and a search follows those links towards the query instead of comparing it with everything.

get_store(ann=True) adds an HNSW index to a store. The SQLite table stays the source of truth. The index is kept in memory and, for a database on disk, saved to a separate file next to it, named <database>.<store>.usearch, which a later connection loads. You can delete that file at any time and rebuild it from the table with rebuild_index().

The index does not follow ordinary inserts. Add rows with Table.sync, which updates the index, or call rebuild_index() after inserting. sync takes the full set of chunks a store should hold. It compares their content hashes with the rows already there, deletes rows that are gone, embeds and inserts the new ones, and updates the index to match. With key_col, it compares only rows whose key_col value appears in the new chunks, so you can re-sync one file or one package without touching the rest.

ann_search searches the index. It fetches twice limit candidates from the index and then applies your where clause to them, so a selective filter can leave nothing. For that reason Database.search(ann=True) switches to the exact vec_search whenever you pass where.

Stores and search, step by step

The rest of this page goes through the same parts as a short tutorial: creating a store, how identifiers survive tokenization, how a hybrid search merges its two legs, and when to add an HNSW index.

get_store(): a table with a full-text index

db.get_store() creates a table, or opens it if it exists, with a content text column, an embedding blob column, a JSON metadata column and an uploaded_at timestamp. It also creates an FTS5 index over content and metadata, kept up to date by triggers. Calling it again is safe.

store = db.get_store()   # idempotent — safe to call multiple times
store.schema
'CREATE TABLE [store] (\n   [content] TEXT NOT NULL,\n   [embedding] BLOB,\n   [metadata] TEXT,\n   [uploaded_at] FLOAT DEFAULT CURRENT_TIMESTAMP,\n   [id] INTEGER PRIMARY KEY\n)'

With hash=True, the id is a SHA-1 hash of the content. Inserting the same text again with upsert=True updates the existing row instead of adding a second one, which removes duplicates for free:

code_store = db.get_store(name='code', hash=True)
code_store.insert_all([{'content':v} for v in ('hello world', 'hi there', 'goodbye now')], upsert=True, hash_id='id')

Identifiers stay whole

The same text through two tokenizer chains:

porter unicode61                                  fts_search running  ->  ft, search, run
porter simplify casefold 1 sanskrit unicodewords  fts_search running  ->  fts_search, run

get_store uses the second chain unless you pass get_store(tokenize=...). tokenize='porter' gives the first.

FTS5 looks the tokenizer up by name each time it reads or writes the index, so every connection to the database must register it, and database() does. A plain sqlite3 connection can read the table, but a full-text query or a write to the store fails with error in tokenizer constructor.

db.search(): keywords and vectors, merged

db.search() runs an FTS5 keyword query and a vector search, then merges the two ranked lists with rrf_all. A row on both lists outranks a row on one. Pass rrf=False to get the two lists back separately.

The query embedding has to come from the same encoder as the stored embeddings, in the same dtype. Here the store holds no embeddings, so both lists are empty.

from litesearch.utils import static_embedder
enc = static_embedder()
q = 'attention mechanism'
db.search(q, enc.encode([q]).ravel().tobytes(), columns=['id','content'], dtype=np.float32, rrf=False)

HNSW for large stores

The default vector search compares the query with every row, which is fast up to a few thousand rows. Beyond that, ann=True keeps an HNSW index in a separate file. The SQLite table remains the source of truth, and store.rebuild_index() rebuilds the index from it at any time.

  • store.sync(content, key_col=..., emb_fn=...) compares content hashes, deletes rows that are gone, embeds and inserts the new ones, and updates the index to match.
  • db.search(..., ann=True) uses the index instead of reading every row.

The cells below load 8,000 code snippets through static_code_embedder and compare the two kinds of vector search. They are not run in CI.

What another connection sees during a write

These tests open a reader and a writer on the same file. While the writer’s write_txn is open, the reader sees neither the new row nor its full-text entry, and both appear once the writer commits. Inside bulk_load the difference shows: the new row is visible, the full-text index does not have it yet, old entries still match, and the rebuild at the end of the block adds it.
